
# EduSight
## AI-Powered Early Academic Risk Detection, Explainability, and Actionable Student Support

**Document:** Master Build & AI-Agent Execution Specification  
**Project Type:** College Mini Project / Production-Oriented AI System  
**Primary Goal:** Build a real, explainable, leakage-safe academic early-warning system using authentic educational data.  
**Development Strategy:** Modular AI-agent-assisted implementation with human verification gates.

---

# 1. Executive Summary

EduSight is an AI-powered academic early-warning system designed to identify students who may be at academic risk early enough for meaningful intervention.

The system is **not simply a classification model**.

The complete system consists of:

1. Authentic educational data ingestion
2. Data quality validation
3. Temporal feature engineering
4. Leakage prevention
5. Academic-risk prediction
6. Probability calibration
7. Risk-threshold selection
8. Explainable AI
9. Counterfactual/actionable recommendations
10. Intervention planning
11. Student dashboard
12. Faculty dashboard
13. Role-based authentication
14. Model monitoring
15. Data/model/version tracking
16. Testing and validation
17. AI-agent-assisted development

The intended flow is:

```text
Authentic Educational Data
        ↓
Data Validation
        ↓
Temporal Feature Engineering
        ↓
Leakage Detection
        ↓
Train / Validation / Test
        ↓
Baseline Models
        ↓
RF / XGBoost / Other Challengers
        ↓
Calibration
        ↓
Risk Threshold
        ↓
Student Risk Probability
        ↓
SHAP Explanation
        ↓
Constrained Counterfactual Analysis
        ↓
Feasibility Validation
        ↓
Action Plan
        ↓
Faculty / Student Dashboard
        ↓
Monitoring + Human Review
```

The system must never fabricate data, model results, features, metrics, explanations, or research findings.

# 2. Core Project Objective

EduSight should answer four practical questions.

### Question 1 — Who may be at risk?

The model predicts an academically relevant future outcome using only information available at the prediction point.

### Question 2 — Why is the student considered at risk?

The system provides model-derived explanations using SHAP and supporting explainability methods.

### Question 3 — What could the student realistically change?

The system generates constrained counterfactual/actionable recommendations.

### Question 4 — What should the faculty member do?

The system converts validated model outputs into an intervention workflow.

---

# 3. Important Scientific Principle

EduSight must distinguish:

```text
Prediction ≠ Causation
```

If SHAP reports that attendance contributed strongly to a prediction, the system must say:

> Attendance was an important factor in this prediction.

It must NOT say:

> Low attendance caused the student to fail.

The latter would require causal evidence that this project does not establish.

# 4. Data Authenticity Policy

This is one of the most important requirements of the entire project.

## 4.1 Real data requirement

All reported:

- accuracy
- precision
- recall
- F1
- ROC-AUC
- PR-AUC
- calibration
- fairness results
- model comparisons
- research conclusions

must come from authentic datasets.

## 4.2 Accepted data sources

### Category A — Public real-world datasets

Examples:

- OULAD
- UCI Predict Students' Dropout and Academic Success

### Category B — Authorized institutional data

If the college provides anonymized academic data with appropriate authorization, it can be used for institutional validation.

### Category C — Synthetic data

Synthetic data may be used ONLY for:

- UI development
- API testing
- unit tests
- edge-case tests
- database testing
- authentication testing
- demonstration of system behavior when authentic data is unavailable

Synthetic data must NEVER be used to claim:

> "Our model achieved X% accuracy."

Synthetic data must also never be silently mixed with real data.

# 5. Dataset Strategy

## 5.1 Primary public dataset — OULAD

OULAD is the preferred dataset for the temporal early-warning component.

The Open University describes OULAD as an anonymized dataset containing courses, students, and interactions with the Virtual Learning Environment. Its tables are connected through identifiers and are distributed as CSV files.

Relevant data includes concepts such as:

- students
- courses/modules
- assessments
- registrations
- VLE activity
- assessment scores
- dates
- interaction counts
- final outcomes

This makes OULAD particularly useful for constructing temporal prediction windows.

---

# 6. Secondary Dataset — UCI Dataset 697

Dataset:

**Predict Students' Dropout and Academic Success**

Official UCI repository:

https://archive.ics.uci.edu/dataset/697/predict+students+dropout+and+academic+success

UCI describes it as data from a higher-education institution involving undergraduate students.

It contains:

- 4,424 instances
- 36 features
- demographic information
- academic-path information
- socioeconomic information
- first-semester performance
- second-semester performance
- macroeconomic variables

Its native target is:

```text
Dropout
Enrolled
Graduate
```

UCI explicitly defines the problem as a three-category classification task.

Therefore:

**Do NOT automatically rename its target to "academic risk".**

Instead, create a clearly documented experimental mapping if a binary risk experiment is required.

Example:

```text
Dropout → Risk
Enrolled → Not automatically risk
Graduate → Not risk
```

If this transformation is used, document it as an experimental target definition.

# 7. UCI Dataset 320 Warning

The classic UCI Student Performance dataset may be useful as an additional benchmark.

However, it represents secondary-school students rather than higher-education students.

Therefore:

**Do not present it as college/university data.**

It should only be used as an optional supplementary benchmark.

# 8. Dataset Mixing Rule

Do NOT blindly concatenate:

```text
OULAD + UCI 697 + UCI 320
```

into one training dataset.

These datasets have:

- different populations
- different institutions
- different feature definitions
- different outcome definitions
- different temporal structures

Instead:

```text
Experiment A → OULAD
Experiment B → UCI 697
Experiment C → optional UCI 320
Experiment D → institutional dataset
```

Each gets its own evaluation protocol.

# 16. PHASE 3 — Leakage Detection

This is a mandatory phase.

The system must identify whether a feature contains information that would not have been available at prediction time.

Example:

```text
Prediction Week = 4
```

Allowed:

```text
Weeks 1–4 attendance
Weeks 1–4 assignments
Weeks 1–4 LMS activity
Weeks 1–4 assessments
```

Not allowed:

```text
Week 5 attendance
Final examination
Final grade
Week 12 assignments
Post-withdrawal information
Final outcome
```

The model must never receive the answer indirectly.

# 17. Temporal Prediction

The core temporal design is:

```text
X(t) → Y(final)
```

Possible experiments:

```text
Week 4 → Final outcome
Week 8 → Final outcome
Week 12 → Final outcome
```

BUT:

**Only create these windows when the actual dataset contains sufficient temporal information.**

Never fabricate week-level data.

For OULAD, derive windows from actual dated interaction/assessment records.

# 24. Threshold Selection

Do not automatically use:

```text
threshold = 0.5
```

Instead:

1. Train model.
2. Generate validation probabilities.
3. Evaluate thresholds.
4. Define intervention cost.
5. Compare false positives and false negatives.
6. Select operating point.
7. Freeze threshold.
8. Evaluate once on untouched test data.

Perform sensitivity analysis:

```text
1:1
2:1
5:1
10:1
```

for false-negative versus false-positive cost assumptions.

The project must report the selected assumption.

# 25. Probability Calibration

A risk probability should be meaningful.

Example:

```text
Predicted risk = 0.80
```

should approximately mean:

```text
students with similar predictions experience the target outcome around 80% of the time
```

where calibration permits that interpretation.

Candidate methods:

```text
Platt scaling
Isotonic regression
```

Evaluate:

```text
Brier score
calibration curve
expected calibration error
```

# 32. Counterfactual Feasibility

Suppose:

```text
Classes completed = 60
Classes attended = 36
Classes remaining = 20
```

Maximum possible final attendance:

```text
(36 + 20) / (60 + 20)
= 70%
```

Therefore the system must never recommend:

```text
Reach 95% attendance
```

because that is mathematically impossible.

The recourse engine must calculate feasibility.

---

# 33. Recourse Objective

Conceptually:

```text
Find minimum-cost actionable changes
such that:

new_prediction < risk_threshold
```

subject to:

```text
immutable feature constraints
range constraints
temporal constraints
feasibility constraints
institutional rules
```

# 34. Action Plan Engine

Counterfactual output should become structured actions.

Example:

```json
{
  "feature": "attendance",
  "current_value": 62,
  "target_value": 70,
  "deadline": "next 3 weeks",
  "priority": "high",
  "reason": "Attendance is contributing to predicted risk",
  "feasible": true
}
```

The system should not invent interventions outside the available evidence.

---

# 35. LLM Usage Rule

An LLM may optionally convert verified structured actions into natural language.

Example:

Structured:

```text
attendance:
62 → 70
feasible: true
priority: high
```

LLM:

> Try to attend the remaining scheduled sessions consistently. Your current attendance is contributing to the model's risk estimate.

The LLM must NOT determine the numerical target itself.

The ML/constraint engine determines:

```text
what
how much
when
whether feasible
```

The LLM only determines:

```text
how to explain it naturally
```
